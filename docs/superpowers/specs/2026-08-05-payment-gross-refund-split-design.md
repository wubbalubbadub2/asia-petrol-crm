# Разделение оплат на «Оплата» и «Возврат/Перезачет»

Дата: 2026-08-05
Статус: утверждено к реализации

## Задача

В сделке у покупателя и у поставщика есть оплаты трёх типов: `payment`
(оплата), `refund` (возврат), `offset` (перезачет). В таблицу сделок
попадает одно агрегированное число на сторону. Нужно показать два числа —
«Оплата» и «Возврат/Перезачет» — и сохранить корректность баланса.

## Что есть сейчас

- `deal_payments.payment_type ∈ ('payment','refund','offset')` (00051, 00062),
  `side ∈ ('supplier','buyer')`, `amount DECIMAL(14,4)` хранится **плюсом**,
  знак задаёт тип.
- `refresh_deal_payment_totals(p_deal_id)` (00062) складывает **нетто**
  (`payment − refund − offset`) в `deals.supplier_payment` /
  `deals.buyer_payment`. Валютный guard: платёж учитывается, только если
  `p.currency IS NULL OR p.currency = <валюта стороны>`.
- Баланс (00021 → 00052 → 00060 → 00112):
  `supplier_balance = приход − supplier_payment (+ жд/ЭСФ по галочкам)`,
  `buyer_debt` — зеркально. То есть возвраты и перезачёты **уже**
  вычитаются, просто не видны отдельной величиной.
- В паспорте одна колонка «Оплата» на сторону с попапом CRUD по оплатам;
  кнопка «Изменить итог» вручную перезаписывает `deals.*_payment` до
  следующего срабатывания rollup-триггера.
- Создать возврат или перезачёт прямо из паспорта сегодня нельзя: кнопка
  «+ Оплата» всегда ставит `payment_type='payment'`.

## Принятые решения

1. «Оплата» = **брутто**, только `payment_type='payment'`.
   «Возврат/Перезачет» = `refund + offset`, показывается **положительным**
   числом. Баланс = приход − (Оплата − Возврат/Перезачет), численно
   идентичен сегодняшнему.
2. Охват: паспорт KG/KZ/Все сделки, карточка сделки, выгрузки Excel
   (паспорт + детальный), отчёт «Сборность».
3. У ячейки «Возврат/Перезачет» — собственный попап только с возвратами и
   перезачётами и кнопками добавления обоих типов.
4. «Изменить итог» остаётся только на ячейке «Оплата» и пишет брутто.

## 1. Данные

### Миграция `00137_payment_gross_refund_split.sql`

Новые колонки на `deals`, тип как у существующих rollup-полей:

| колонка | смысл |
|---|---|
| `supplier_payment_gross DECIMAL(14,4) DEFAULT 0` | Σ `amount` где `payment_type='payment'`, сторона `supplier` |
| `supplier_refund_total DECIMAL(14,4) DEFAULT 0` | Σ `amount` где `payment_type IN ('refund','offset')`, сторона `supplier` |
| `buyer_payment_gross DECIMAL(14,4) DEFAULT 0` | то же по стороне `buyer` |
| `buyer_refund_total DECIMAL(14,4) DEFAULT 0` | то же по стороне `buyer` |

`refresh_deal_payment_totals(p_deal_id)` переписывается через
`CREATE OR REPLACE` и заполняет шесть значений за один проход:

```
gross   = Σ amount WHERE payment_type = 'payment'
refund  = Σ amount WHERE payment_type IN ('refund','offset')
payment = gross − refund            -- ровно то же число, что сегодня
```

Валютный guard из 00043/00051/00062 сохраняется дословно: платёж в валюте,
отличной от валюты стороны, не попадает **ни в одну** из трёх сумм.
Ветка `IF NOT FOUND` (сделка без оплат) обнуляет все шесть колонок.

Триггеры вызова rollup (INSERT/UPDATE/DELETE по `deal_payments`) не
меняются.

### Бэкфилл

В той же миграции — прогон `refresh_deal_payment_totals(id)` по всем
сделкам, у которых есть строки в `deal_payments`. У остальных сделок
остаются нули из `DEFAULT`. Существующие значения `supplier_payment` /
`buyer_payment` пересчитываются в те же числа (формула нетто не изменилась),
кроме сделок с активным ручным переопределением итога — оно и сегодня
живёт только до следующего изменения строк оплат.

### Баланс

`compute_deal_derived_fields` **не трогаем**. `supplier_balance` и
`buyer_debt` продолжают читать нетто-колонки. Единица, валюта, округление,
дата-основа, знаковая конвенция — без изменений.

### Инварианты

- `supplier_payment_gross ≥ 0`, `supplier_refund_total ≥ 0` (то же для buyer).
- `supplier_payment = supplier_payment_gross − supplier_refund_total` —
  кроме окна ручного переопределения итога.
- Платёж в чужой валюте не входит ни в gross, ни в refund, ни в нетто.

### Тест `supabase/tests/07_payment_gross_refund.test.sql`

| сценарий | ожидание |
|---|---|
| норма: 2 оплаты (100 + 200) + возврат 30 + перезачёт 20 | gross 300, refund 50, нетто 250, баланс = приход − 250 |
| граница: только возврат 40, оплат нет | gross 0, refund 40, нетто −40, баланс = приход + 40 |
| реверс: удалить возврат из первого сценария | gross 300, refund 20, нетто 280 |
| смена типа `payment → refund` у существующей строки | суммы переехали между колонками, нетто уменьшилось вдвое от суммы строки |
| платёж в валюте ≠ валюты стороны | не попал ни в одну из трёх колонок |
| сделка без оплат | все шесть колонок = 0 |

## 2. Паспорт (`src/components/deals/passport-table.tsx`)

Две новые колонки, каждая сразу после «Оплата» в своей полосе:

```
… Приход,тонн │ Оплата │ Возврат/Перезачет │ Баланс │  Поставщик: 10 → 11
… Отгр.сумма  │ Оплата │ Возврат/Перезачет │ Долг   │  Покупатель: 11 → 12
```

Таблица завязана на позиционные индексы, поэтому обязательны все правки:

- `TOTAL_COLS` 36 → 38 (спейсеры виртуализации, colSpan).
- `PT_UNITS`: +2 записи (`supplier_refund`, `buyer_refund`) и сдвиг
  `h`/`body` у всех единиц после `h14` и после `h28`. Комментарий про
  «36 видимых колонок» обновить.
- colSpan заголовков полос «Поставщик» и «Покупатель».
- Итоговая строка: +2 суммируемые ячейки в нужных позициях.
- `NUMERIC_COLS`: +2 ключа, чтобы новые колонки участвовали в
  Excel-подобном выделении с суммой.

Новые ключи колонок по умолчанию видимы; сохранённые в `user_prefs`
настройки скрытия и закрепления продолжают работать — незнакомых ключей в
них просто нет.

### Ячейка «Оплата»

Показывает `*_payment_gross`. Попап фильтруется до `payment_type='payment'`;
кнопка «+ Оплата» без изменений. «Изменить итог» остаётся здесь и пишет
брутто: `*_payment_gross = X` и `*_payment = X − *_refund_total`.

### Ячейка «Возврат/Перезачет»

Показывает `*_refund_total` положительным числом. Собственный попап: только
строки `refund` и `offset`, у каждой метка типа (компонент уже её рисует),
кнопки **«+ Возврат»** и **«+ Перезачёт»**. Кнопки «Изменить итог» нет.
Это закрывает существующую дыру: создать возврат из паспорта сегодня
невозможно.

### Оптимистичное обновление

Правило клиента «на фронте меняем сразу, как в Excel» сохраняется.
Обобщение: `Δнетто = Δбрутто − Δвозвратов`, дальше как сейчас —
`supplier_balance −= Δнетто`, `buyer_debt += Δнетто`. Патчатся все три
колонки строки. Откат при ошибке — как сегодня.

## 3. Карточка сделки (`src/app/(dashboard)/deals/[id]/page.tsx`)

В блоках Поставщик и Покупатель поле «Оплата» переводится на брутто; рядом
добавляется read-only поле «Возврат/Перезачет». Это убирает расхождение
ярлыков между карточкой и паспортом.

## 4. Выгрузки Excel

`src/lib/exports/passport-excel.ts` — колонка «Возврат/Перезачет» сразу
после «Оплата» в обеих полосах, из новых полей, формат `NUM_FMT_AMOUNT`.

`src/lib/exports/passport-detail-excel.ts` — то же на строке сделки. В
под-строках каждая оплата попадает в колонку **по своему типу**: `payment`
→ «Оплата», `refund`/`offset` → «Возврат/Перезачет» положительным числом.
Сегодня возврат идёт минусом в «Оплата» — это осознанное изменение вида
детальной выгрузки ради согласованности с экраном. `PaymentLite` получает
поле типа вместо предподписанной суммы. В FX-режиме (`convertDeal`)
подставляются брутто и возвраты из отчётной функции, а не из полей сделки.

## 5. Отчёт «Сборность»

Отчёт целиком клиентский, в БД лезть не нужно.

- `src/lib/data/deal-events.ts` перестаёт схлопывать знак на загрузке и
  передаёт `payment_type` дальше.
- `src/lib/fx/convert-deal.ts`: `PaymentRow` получает тип; `FxDealRow` —
  `supplierPaymentGross`, `supplierRefund`, `buyerPaymentGross`,
  `buyerRefund`. Баланс и долг внутри считаются по нетто
  (`gross − refund`), чтобы паритет с паспортом сохранился дословно.
  Правило «хоть одно событие не сконвертировалось → null» распространяется
  на обе новые величины.
- `src/components/reports/collection-table.tsx`: +2 колонки с итогами.

Тесты в `src/__tests__/fx-convert-deal.test.ts`: сделка с возвратом даёт
gross и refund раздельно, а баланс совпадает с паспортным.

## 6. Вне охвата

используются нетто-суммы, они остаются корректными; разделение не
