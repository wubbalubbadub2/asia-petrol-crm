# Этап 1. Дислокация и сверхнормативный простой вагонов

Дата: 2026-09-27. Статус: черновик на согласование.
Исходные материалы и доказательства: `asia petrol/logistics-analysis-2026-09-27/` (SUMMARY.md, dislocation.md,
protocols.md, demurrage-registries.md, repo-map.md).

## 1. Цель и критерий успеха

Логист загружает ежедневные файлы дислокации, заводит протокол согласования цены экспедитора, и CRM сама
считает сверхнормативный простой по каждому вагону: отдельно погрузка, отдельно выгрузка, итог, сумма.

**Критерий успеха (приёмочный тест клиента):** клиент загружает файлы Шагыр → Кара-Балта за 19.08–04.09.2026,
заводит протокол, получает реестр простоя в формате реестра PTC и сверяет его с реестром экспедитора.
Каждая дата в реестре CRM показывает, откуда она взята, и помечена, если требует проверки.

## 2. Решения по умолчанию (можно переопределить до плана)

1. Этап 1 — первым; план отгрузок и сальдо — этапы 3 и 4.
2. Заявку на перевозку со сделкой **не связываем** на этапе 1. Простой без накладной показываем отдельным
   списком «Стоянки без отгрузки» (экспедитор × станция × вагон), без привязки к сделке.
3. Экспедитор файла выбирается при загрузке. Для Шагыр экспедитора укажет логист; код от него не зависит.
4. Формат файла на этапе 1 — только 1С «Рассылка дислокации» (PTC и Шагыр). Формат Prologistic — этап 2.

## 3. Бизнес-правила

Источники правил — ответы клиента от 27.09, Протокол № 20, реестры PTC за июль (проверено 487/487 строк).

### 3.1 Рейс и стоянка

- **Рейс** = вагон + номер накладной. Заглушка `00000000` рейсом не считается: берётся номер из следующего
  снимка того же вагона. Дата накладной берётся из **последнего** снимка рейса: в первый день у порожнего
  рейса дата на сутки позже (38/38 случаев).
- **Груж/Порож** рейса — по колонке «Груж\Порож».
- **Стоянка на погрузке** — между порожним рейсом, у которого станция назначения X, и следующим гружёным
  рейсом со станцией отправления X.
- **Стоянка на выгрузке** — между гружёным рейсом со станцией назначения Y и следующим порожним рейсом
  со станцией отправления Y.

### 3.2 Даты стоянки

| Граница | Источник | Правило |
|---|---|---|
| Прибытие порожнего на станцию погрузки | дислокация | дата самой ранней «даты последней операции» среди снимков, где вагон стоит на X в порожнем рейсе на X |
| Отправление гружёного | дислокация, дата ЖДН гружёного рейса | клиент: «превалирует дата ЖД-накладной» |
| Прибытие гружёного на станцию выгрузки | дислокация | то же правило, что для прибытия порожнего (вопрос клиенту № 1) |
| Отправление порожнего | дислокация, дата ЖДН порожнего рейса | из последнего снимка рейса |

**Признак «требует проверки»** ставится на дату прибытия, если в первом снимке на станции «дата последней
операции» позже, чем «снимок − простой на станции дислокации». Значит, между снимками был пропуск.
Тогда показываем оба варианта даты, а в расчёт идёт более ранняя. Решение по спорной дате — за логистом,
правка даты вручную хранится отдельно от вычисленной и помечается автором.

**Незакрытая стоянка:** нет даты ухода — расчёт предварительный, конец = дата последнего снимка.
Становится окончательным, когда появляется накладная следующего рейса.

### 3.3 Формула

Все даты — `date`, без часовых поясов. Для стоянки с прибытием `A`, уходом `D`, нормой `N` суток:

- если протокол «день прибытия считается» (`arrival_day_counts = true`, по умолчанию):
  нормативные сутки `A … A+N−1`, сверхнормативные `A+N … D`;
- если «со следующих суток»: нормативные `A+1 … A+N`, сверхнормативные `A+N+1 … D`.

`сверх = max(0, число сверхнормативных суток)`. Для случая «день прибытия считается» это
`max(0, (D − A) + 1 − N)` — совпадает с реестрами PTC. Пример клиента: 01.08 → 11.08, норма 3 → 8 суток.

`сумма = сверх × ставка за вагон-сутки`. Валюта и признак НДС — из протокола. Округления нет, числа целые.

**Сутки по месяцам:** в реестр месяца идут только сверхнормативные сутки, попавшие в этот месяц. Хвост
прошлого месяца — отдельной строкой «сутки <месяца>», как у PTC.

### 3.4 Протокол согласования цены

Протокол выбирается по экспедитору, станции отправления гружёного рейса, станции назначения и дате
гружёного рейса внутри периода действия. Если протоколов несколько — ошибка «неоднозначный протокол»,
расчёт не делается. Если протокола нет — стоянка показывается, сумма пустая, статус «нет протокола».

Изменение ставки — новый протокол с новым периодом. Старые периоды не пересчитываются, потому что
выбирается протокол, действовавший на дату рейса. Правка уже действующего протокола пересчитывает его
период — это видно в журнале изменений.

### 3.5 Привязка к сделке

Гружёный рейс ищется в реестре отгрузок по паре (номер вагона, номер накладной). Найден — показываем
сделку и компанию группы. Не найден — «нет в реестре», расчёт всё равно делается.

## 4. Данные

Новые таблицы с префиксом `rail_` — схема `public` общая со вторым продуктом.

- `rail_dislocation_uploads` — файл: экспедитор, дата и время снимка (из имени файла, подтверждает
  пользователь), имя файла, хэш содержимого (уникальный — повторная загрузка того же файла запрещена),
  кто загрузил, число строк.
- `rail_dislocation_rows` — строка файла: все поля парсера `DislocationRow` + `upload_id`. Уникально
  (upload_id, wagon_number).
- `rail_station_aliases` — название станции из файла (нормализованное) → `stations.id`. При загрузке
  нераспознанные названия пользователь сопоставляет со справочником один раз.
- `rail_price_protocols` — экспедитор, компания группы, номер, дата, период с/по, ставка за вагон-сутки,
  валюта, НДС в ставке, «день прибытия считается», «неполные сутки = полные» (для отчёта), примечание,
  скан PDF (необязательно).
- `rail_price_protocol_routes` — строки протокола: станция отправления, станция назначения, груз,
  норма погрузки, норма выгрузки, ж/д тариф $/т, услуги оператора $/т, ТЭО $/т. Ставки за тонну на
  этапе 1 только хранятся — пригодятся в этапах 2–4.
- `rail_stay_overrides` — ручная правка даты стоянки: вагон, накладная, какая граница, новая дата,
  причина, автор.

Вычисления — представления в PostgreSQL с `security_invoker`, по образцу отчёта «Условия оплаты»:
`rail_wagon_trips` → `rail_wagon_stays` → `rail_demurrage` (стоянка + протокол + сумма) →
`rail_demurrage_by_month`. Деньги в React не считаются.

RLS: читают все вошедшие, пишут `is_writable_role()` (роль `logistics` в неё входит), удаляет админ.
Файлы-сканы протоколов — в существующем бакете заявок на перевозку, отдельной папкой.

## 5. Экраны

Новый пункт меню «Дислокация»:

1. **Загрузка** — выбрать экспедитора и файлы (несколько сразу), подтвердить дату снимка, сопоставить
   новые станции, увидеть «загружено N вагонов, ошибок M».
2. **Простой** — таблица стоянок: вагон, станция, погрузка/выгрузка, прибытие, уход, норма, сутки,
   сверх, сумма, статус (окончательный / предварительный / требует проверки / нет протокола), сделка.
   Фильтры: экспедитор, месяц, станция, статус. Выгрузка Excel в формате реестра PTC (колонки A–R:
   клиент, станции, груз, вагон, 4 даты, 2 нормы, ставка, сверх налив/слив, итого дней, сумма,
   примечание, валюта).
3. **Вагон** — лента снимков и рейсов одного вагона, откуда взята каждая дата, ручная правка даты.
4. **Протоколы цены** — список и форма с таблицей маршрутов.

Интерфейс по DESIGN.md: плотные таблицы, русский язык, клавиатура.

## 6. Приёмочные сценарии

Данные — реальные файлы Шагыр из архива клиента.

1. **Выгрузка, без сверхнорматива.** Вагон 70524723: гружёный рейс Д0394175 от 18.08; снимок 21.08 —
   Кара-Балта, операция 20.08 15:01; порожний рейс 04005810 от 21.08. Стоянка выгрузки 20.08–21.08 =
   2 суток, норма 3 → сверх 0, сумма 0.
2. **Формула клиента.** Прибытие 01.08, уход 11.08, норма 3, «день прибытия считается» → 11 суток,
   сверх 8, при ставке 35 → 280 USD. При «со следующих суток» → сверх 7, 245 USD.
3. **Переход месяца.** Прибытие 29.07, уход 05.08, норма 2 → сверхнормативные сутки 31.07–05.08: июль 1,
   август 5.
4. **Заглушка накладной.** Вагон 73932139, порожний рейс: в снимке 24.08 накладная `00000000` от 24.08, в снимке 25.08 —
   04005923 от 23.08. Рейс один, дата отправления 23.08.
5. **Незакрытая стоянка.** Вагон стоит на Шагыр под погрузкой в последнем снимке 04.09 → статус
   «предварительный», конец = 04.09.
6. **Нет протокола.** Стоянка без подходящего протокола → сутки считаются, сумма пустая, статус
   «нет протокола».
7. **Повторная загрузка** того же файла → отказ с понятным сообщением, данные не задваиваются.
8. **Файл не той формы** (Prologistic) → «формат не поддерживается», ничего не записано.
9. **Права.** Роль без записи видит отчёт, но не может загрузить файл или изменить протокол.

## 9. Открытые вопросы клиенту — не блокируют этап 1

Каждый закрыт настройкой или пометкой в отчёте, ответ меняет только значение по умолчанию.

1. Дата прибытия гружёного на станцию выгрузки — по дислокации? (сейчас — да)
2. Смысл кодов ОТПР, ПРИБ, ПВПП. Расчёт от кодов не зависит, только от станции и Груж/Порож.
3. НДС в ставке 35 USD — поле протокола.
4. «День прибытия считается» — поле протокола, по умолчанию «да».
5. Снимок Шагыр за 26.08 отсутствует — стоянки через 26.08 получат пометку «требует проверки», если
   пропуск влияет на дату.
